# Evolution API deployment

This directory contains a Render Blueprint for the Gravity RSVP WhatsApp worker.
The RSVP form data remains in Google Sheets. Supabase stores only Evolution's
internal database and linked-device state.

## 1. Create Supabase PostgreSQL

1. Create a dedicated Supabase project in a region close to Render Singapore.
2. Open **SQL Editor** and run `supabase-setup.sql`. This creates only the
   private `evolution_api` schema and removes access from Supabase's `anon` and
   `authenticated` roles.
3. Open **Connect** and choose **Session pooler**.
4. Copy the port `5432` connection string. Replace the password placeholder,
   URL-encode any reserved password characters, and add
   `?schema=evolution_api&sslmode=require`.
5. Keep the database password and complete connection string private.

Do not create RSVP tables in Supabase and do not expose a Supabase service-role
key to the RSVP application.

### What creates the tables?

Do not manually deploy Evolution table DDL. On its first successful boot, the
pinned Evolution `v2.3.7` container uses its bundled Prisma migrations to create
and version all required tables inside `evolution_api`. On later boots it applies
only outstanding migrations. `supabase-setup.sql` includes a read-only query to
verify the result.

The exact Evolution table list is implementation-owned and can change with a
pinned-version upgrade. Gravity RSVP data is not copied there: form records and
email/WhatsApp delivery columns remain in Google Sheets.

## 2. Deploy the Blueprint

1. In Render choose **New > Blueprint**.
2. Select this repository.
3. Set the Blueprint path to `evolution-deploy/render.yaml`.
4. Provide `DATABASE_CONNECTION_URI` using the Supabase Session pooler URL.
5. Set `SERVER_URL` to the final HTTPS Render service URL. If Render assigns a
   different subdomain, update this environment variable after provisioning.
6. Keep the generated `AUTHENTICATION_API_KEY` secret.

`render.yaml` is the deployable configuration. `example.env` is the annotated
inventory of every variable and explains where each non-default value comes
from. Do not upload `example.env` as a Render secret file; the Blueprint already
defines the variables.

## Environment value inventory

### Values you must supply to Render

| Variable | Where it comes from |
|---|---|
| `DATABASE_CONNECTION_URI` | Supabase **Connect > Session pooler**, port `5432`; add `schema=evolution_api` and `sslmode=require` |
| `SERVER_URL` | The public HTTPS URL Render assigns to the Web Service |

### Value Render creates

| Variable | Where it comes from |
|---|---|
| `AUTHENTICATION_API_KEY` | Generated by the Blueprint using Render's `generateValue: true`; copy it from the Render service Environment page only when configuring Apps Script |

All other Render values are non-secret operational defaults committed in
`render.yaml`. You do **not** need `SUPABASE_URL`, `SUPABASE_ANON_KEY`, or
`SUPABASE_SERVICE_ROLE_KEY` because Evolution connects directly to PostgreSQL.

### Values copied into Apps Script

| Script Property | Source |
|---|---|
| `EVOLUTION_BASE_URL` | Same Render URL as `SERVER_URL` |
| `EVOLUTION_API_KEY` | Same Render secret as `AUTHENTICATION_API_KEY` |
| `EVOLUTION_INSTANCE_NAME` | Fixed value `gravity-rsvp` |
| `WHATSAPP_DEFAULT_COUNTRY_CODE` | Fixed value `91` |
| `WHATSAPP_BATCH_SIZE` | Fixed initial value `10` |
| `WHATSAPP_TEST_NUMBER` | Your internal test WhatsApp number, digits with country code |
| `APPS_SCRIPT_SHARED_SECRET` | A separate random secret that you generate and also add to Vercel |

### Values configured in Vercel

| Variable | Source |
|---|---|
| `APPS_SCRIPT_URL` | Apps Script **Deploy > Manage deployments > Web app URL**, ending in `/exec` |
| `APPS_SCRIPT_SHARED_SECRET` | Exactly the same separate secret stored in Apps Script |

The Evolution API key and the Apps Script shared secret serve different
purposes and should not be the same value.

Render Free sleeps after inactivity and is intended only for the pilot. Complete
the restart and cold-start tests in `EVOLUTION_API_INTEGRATION_SPEC.md` before
using the service for guest invitations.

### Git-backed Dockerfile alternative

If Render requires card verification for an **Existing Image** or Blueprint
deployment, create a regular Git-backed Web Service instead:

1. Choose **New > Web Service** and connect this GitHub repository.
2. Set **Root Directory** to `evolution-deploy`.
3. Select **Docker** as the runtime. Render will use `Dockerfile` from that
   directory; do not enter Yarn build or start commands.
4. Choose the **Free** instance.
5. Set the health-check path to `/`.
6. Paste the variables from `example.env`, replacing the required inputs.

The wrapper Dockerfile inherits the official image's startup command and pins
the same `v2.3.7` release as the Blueprint.

### AWS EC2 reconnect-patched image

Some WhatsApp multi-device logins emit a normal `515` reconnect followed by a
`401 device_removed` event. Evolution API 2.3.7 can misclassify that sequence as
a permanent logout (upstream issue `evolution-foundation/evolution-api#2498`).

`Dockerfile.aws-patched` builds the official `2.3.7` tag from source and applies
only the 30-second reconnect guard proposed for that issue. It does not change
the API contract, database migrations, or message endpoints.

Build it on EC2 from this directory:

```bash
docker build -f Dockerfile.aws-patched -t gravity-rsvp-evolution:2.3.7-515fix .
```

The build requires more memory than the runtime container. On a 2 GB EC2
instance, create temporary swap before building and remove it after the patched
image is running. Continue to mount `evolution_instances` at
`/evolution/instances` and bind the API only to `127.0.0.1:10000` behind Caddy.

## 3. Create and connect the instance

Run these requests from a trusted terminal, replacing the placeholders locally.
Never paste the API key into a public issue, screenshot, or committed file.

Create the instance:

```bash
curl -X POST "https://YOUR-SERVICE.onrender.com/instance/create" \
  -H "Content-Type: application/json" \
  -H "apikey: YOUR_API_KEY" \
  -d '{"instanceName":"gravity-rsvp","integration":"WHATSAPP-BAILEYS","qrcode":true}'
```

Request the QR code:

```bash
curl "https://YOUR-SERVICE.onrender.com/instance/connect/gravity-rsvp" \
  -H "apikey: YOUR_API_KEY"
```

Scan it in WhatsApp Business under **Settings > Linked devices > Link a device**.

Check connection state:

```bash
curl "https://YOUR-SERVICE.onrender.com/instance/connectionState/gravity-rsvp" \
  -H "apikey: YOUR_API_KEY"
```

The expected state is `open` or `connected`.

## 4. Configure Apps Script

In Apps Script open **Project Settings > Script properties** and add:

| Property | Value |
|---|---|
| `EVOLUTION_BASE_URL` | Render HTTPS service URL |
| `EVOLUTION_API_KEY` | Render's generated API key |
| `EVOLUTION_INSTANCE_NAME` | `gravity-rsvp` |
| `WHATSAPP_DEFAULT_COUNTRY_CODE` | `91` |
| `WHATSAPP_BATCH_SIZE` | `10` |
| `WHATSAPP_TEST_NUMBER` | Internal test number with country code |
| `APPS_SCRIPT_SHARED_SECRET` | Same random value configured in Vercel |

Also add `APPS_SCRIPT_SHARED_SECRET` to the Vercel project environment. Deploy
the updated Apps Script before setting this secret so the transition does not
interrupt live submissions.

## 5. Apps Script setup order

1. Replace the deployed Apps Script source with `gravity-rsvp-appsscript.gs`.
2. Run `setupSheet()` and authorise it. This appends K:Q and does not clear A:J.
3. Run `testPhoneNumberNormalization()`.
4. Run `checkEvolutionConnection()`.
5. Run `testEvolutionText()` and verify the internal text message.
6. Run `testEvolutionPdf()` and verify one internal test PDF.
   The first send creates a private **Gravity RSVP 2026 Generated Passes**
   folder in the Apps Script owner's Drive. Email and WhatsApp both reuse the
   same saved PDF; the files are never made public.
7. Run `installSweepTrigger()` if the five-minute trigger is not already present.
8. Create a new Apps Script web-app deployment version.
9. Confirm the Vercel `APPS_SCRIPT_URL` still points to the `/exec` deployment.

## 6. Required launch checks

- Google Sheet columns A:J and old rows are unchanged.
- A new RSVP appears in Google Sheets even when Evolution is stopped.
- Email succeeds independently of WhatsApp.
- A consenting test RSVP receives exactly one WhatsApp PDF.
- A non-consenting RSVP receives email only.
- Render restart does not require QR pairing again.
- Render Free cold-start recovery succeeds.
- `whatsappStatusReport()` shows no unreviewed `Unknown` rows.

## What is deployed where

| Destination | Artifact/configuration |
|---|---|
| GitHub | Application source, `evolution-deploy/render.yaml`, documentation, tests; no secrets |
| Supabase | `evolution_api` schema boundary, followed automatically by Evolution's Prisma tables |
| Render | Pinned `evoapicloud/evolution-api:v2.3.7` image using `render.yaml` |
| Apps Script | Latest `gravity-rsvp-appsscript.gs`, Script Properties, `setupSheet()`, and sweep trigger |
| Vercel | GitHub application deployment plus `APPS_SCRIPT_URL` and shared secret |
| Google Sheet | Existing A:J preserved; `setupSheet()` appends K:Q |

## Deployment order

1. Push this repository to GitHub.
2. Create Supabase and run `supabase-setup.sql`.
3. Create the Render Blueprint from `evolution-deploy/render.yaml`; enter its
   two required values.
4. Correct `SERVER_URL` after the service URL is known and redeploy.
5. Create the `gravity-rsvp` instance, scan its QR, and confirm state `open`.
6. Deploy Apps Script, add its properties, and run the setup/test functions.
7. Add/update the two Vercel variables and redeploy the website.
8. Run internal test numbers, then the ten-person pilot.
